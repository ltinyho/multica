# Android Notifications and APK Build Variants

This document records the Android notification changes carried on top of the
upstream Expo / React Native mobile app. Use it when rebasing onto a newer
official Multica release, rebuilding APKs, or debugging notification behavior.

## Current Behavior

There are three Android APK variants:

| Variant | Script | Backend | Foreground service | Intended test |
| --- | --- | --- | --- | --- |
| `fg` | `pnpm -C apps/mobile android:apk:prod:fg` | self-host from `.env.production` | enabled | Background inbox polling with a persistent notification |
| `nofg` | `pnpm -C apps/mobile android:apk:prod:nofg` | self-host from `.env.production` | disabled | No persistent notification; only app-online realtime notifications |
| `official` | `pnpm -C apps/mobile android:apk:official` | built-in official defaults | disabled | Clean official-domain build without loading `.env.production` |

All APKs are copied to `~/Downloads`. Their filenames and `versionName` include
the variant and timestamp, for example:

```text
multica-fg-0.1.0-fg-20260530212648.apk
multica-nofg-0.1.0-nofg-20260530213330.apk
multica-official-0.1.0-official-20260530214100.apk
```

The app package id remains `ai.multica.mobile`, so these APKs replace each other
when installed. Uninstall or install over the previous build depending on what
you want to test.

## URLs

Self-host builds read `apps/mobile/.env.production`:

```env
VITE_API_URL=https://mate-api.adevjoe.com
VITE_WS_URL=wss://mate-api.adevjoe.com/ws
VITE_APP_URL=https://mate.adevjoe.com

EXPO_PUBLIC_API_URL=https://mate-api.adevjoe.com
EXPO_PUBLIC_WS_URL=wss://mate-api.adevjoe.com/ws
EXPO_PUBLIC_WEB_URL=https://mate.adevjoe.com
```

The `official` build deliberately does not load `.env.production`. It uses
defaults from `apps/mobile/lib/urls.ts`:

```ts
DEFAULT_API_URL = "https://api.multica.ai";
DEFAULT_WS_URL = "wss://api.multica.ai/ws";
DEFAULT_WEB_URL = "https://multica.ai";
```

`android:apk:official` sets `EXPO_NO_DOTENV=1` and clears any inherited URL
environment variables before running the build. Keep that behavior; otherwise
Expo can auto-load `.env.production` and accidentally produce another self-host
APK.

## Notification Paths

Android has two possible notification paths:

1. Native foreground service polling `/api/inbox` every 5 seconds.
2. JS WebSocket `inbox:new` notification while the app process is alive.

Only one path should notify on Android at a time:

- `fg`: native foreground service sends inbox notifications; JS `inbox:new`
  only invalidates the inbox query.
- `nofg` / `official`: foreground service is not registered or started; JS
  `inbox:new` sends the notification.

This split avoids duplicate notifications for the same inbox item.

Task completion notifications are intentionally not sent as generic
`Task completed` notifications. Concrete task-related inbox items still notify.
Task failure notifications remain supported.

## Foreground Service

The foreground service is generated by the Expo config plugin:

```text
apps/mobile/plugins/with-foreground-inbox-service.js
```

Do not edit `apps/mobile/android/` directly. It is generated by Expo prebuild.

The service:

- stores the token, workspace slug, and API URL in Android shared preferences;
- starts a `dataSync` foreground service;
- holds a partial wake lock;
- polls `GET /api/inbox` every 5 seconds;
- notifies only unread, unarchived items whose ids have not been notified
  before;
- uses the high-priority channel `multica_inbox_alerts_v2` for inbox alerts;
- uses a low-priority persistent channel for the service notification.

The persistent foreground notification is intentionally static:

```text
Multica
Checking inbox in the background
```

Do not update it on every poll. Dynamic updates caused the persistent
notification to visibly flash.


for bottom tabs, because Android release builds can render only the labels and
no icons.

## Build Commands

Run typecheck first:

```bash
pnpm -C apps/mobile typecheck
```

Build all three APKs:

```bash
pnpm -C apps/mobile android:apk:prod:fg
pnpm -C apps/mobile android:apk:prod:nofg
pnpm -C apps/mobile android:apk:official
```

The scripts call `expo prebuild --platform android --no-install --clean`, then
`./gradlew assembleRelease`, then copy the release APK into both the generated
Android output directory and `~/Downloads`.

## Verification

Use the current Android SDK build-tools version installed on the machine. This
repo has used `36.0.0`:

```bash
APK=/home/ltinyho/Downloads/multica-fg-0.1.0-fg-YYYYMMDDHHMMSS.apk

/home/ltinyho/Android/Sdk/build-tools/36.0.0/aapt dump badging "$APK" | sed -n '1p'
/home/ltinyho/Android/Sdk/build-tools/36.0.0/aapt dump permissions "$APK" \
  | rg 'FOREGROUND|POST_NOTIFICATIONS|WAKE_LOCK|VIBRATE|INTERNET'
/home/ltinyho/Android/Sdk/build-tools/36.0.0/apksigner verify --verbose "$APK"
```

Expected permission differences:

- `fg` includes `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_DATA_SYNC`.
- `nofg` and `official` do not include foreground service permissions.
- All variants include `POST_NOTIFICATIONS`, `INTERNET`, and `VIBRATE`.

For `official`, also verify the bundle does not contain self-host domains:

```bash
rm -rf /tmp/multica-apk-check
mkdir -p /tmp/multica-apk-check
unzip -p /home/ltinyho/Downloads/multica-official-*.apk assets/index.android.bundle \
  > /tmp/multica-apk-check/official.bundle

grep -ao 'mate-api\.adevjoe\.com' /tmp/multica-apk-check/official.bundle | wc -l
grep -ao 'mate\.adevjoe\.com' /tmp/multica-apk-check/official.bundle | wc -l
grep -ao 'api\.multica\.ai' /tmp/multica-apk-check/official.bundle | wc -l
grep -ao 'multica\.ai' /tmp/multica-apk-check/official.bundle | wc -l
```

The first two counts must be `0`; official domains should be present.

## Runtime Testing Notes

For `fg`:

1. Install the `fg` APK.
2. Log in and enter a workspace.
3. Confirm Android shows the persistent `Multica` notification.
4. Send or create an inbox item from another client.
5. The inbox alert should come from the `Multica inbox alerts` channel.
6. The persistent notification should not flash every 5 seconds.

For `nofg` and `official`:

1. Install the APK.
2. Log in and keep the app process alive.
3. Switch to another app if desired, but remember Android can suspend or kill
   JS when the app is backgrounded.
4. Send an inbox item from another client.
5. Notification delivery depends on the WebSocket still being alive.

Android banner / heads-up display also depends on system channel settings. Check
the `Multica inbox alerts` channel specifically, not only the global app
notification permission.

## Reapplying After an Official Update

When the official project releases new code, prefer replaying the local Android
notification commits onto the updated base rather than editing generated Android
files.

Suggested flow:

```bash
# 1. Save any local work first.
git status --short

# 2. Fetch the official upstream. Adjust remote/branch names to the local setup.
git fetch upstream

# 3. Create a fresh branch from the official release branch.
git checkout -b mobile-notifications-android-refresh upstream/main

# 4. Reapply the Android notification/APK commits in order.
git cherry-pick 560d7c7a 09b33d10 e5ac4893 9ead0012 a6175bd3
```

If commit hashes are unavailable, port the files listed in "Important Files"
and preserve these invariants:

- Android native changes must live in Expo config plugins, not `apps/mobile/android/`.
- `fg` and `nofg` must not both send Android inbox notifications.
- `official` must not load `.env.production`.
- The foreground persistent notification must stay static.
- Bottom tab icons must use Android-safe icons such as `Ionicons`.
- APK filenames and version names must include the variant and timestamp.
- Build scripts must copy APKs to `~/Downloads`.

After resolving conflicts, run:

```bash
pnpm -C apps/mobile typecheck
pnpm -C apps/mobile android:apk:prod:fg
pnpm -C apps/mobile android:apk:prod:nofg
pnpm -C apps/mobile android:apk:official
```

Then run the verification commands above before handing APKs to a tester.
